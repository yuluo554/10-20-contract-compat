# 10-20-contract-compat · 跨格式契约兼容性判定器（题目文档）

> - **性质**：不参赛项目题（无赛事锚点；含金量锚点 = 需求侧原话 + 已占位工具的覆盖边界实测 + 开源空白检索）
> - **目标产出**：仓库 `10-20-contract-compat`（ContractCompat / 跨格式契约兼容性判定器），发布 GitHub **公开仓库**，署名 yuluo554
> - **版本史**：v1 2026-10-20（初稿定稿；查证基准日 **2026-10-20**）
> - **交付形态**：**纯本地双文件 CLI**（输入两份 schema 文件，输出一张判定表；零 registry、零网络、零 Kafka、零模型）。唯一形态，不设备选。
> - **定位宣言**："buf 用 `FILE/PACKAGE/WIRE_JSON/WIRE` 四档，Confluent 用 `BACKWARD/FORWARD/FULL` 七档，JSON Schema 生态各说各话——**同一个『删字段』在三种格式里被两套黑话描述，跨格式团队必然误判**。本工具把 Avro / Protobuf / JSON Schema 三种 schema 归一到同一套判定语汇，输出同一张表：破例规则、稳定路径（字段号 / JSON Pointer）、**砸的是老消费者还是新消费者**、最小修复动作。"

## 一、介绍

### 1.1 痛点

同一支团队在同一个事件总线上同时跑 Avro、Protobuf、JSON Schema 是常态（历史包袱 + 不同语言栈的默认序列化），但**兼容性判定语汇是格式私有的**：

1. **黑话不通**：`buf breaking` 说"这个改动只在 `WIRE` 档破坏"，Confluent Schema Registry 说"这违反 `BACKWARD`"，JSON Schema 生态干脆没有官方档位——三条结论都说"有问题"或都说"没问题"，却无法回答"同一个改动换格式后是不是同一种破坏"。团队于是按最宽松的那套理解放行。
2. **方向性无人回答**：schema 演化本身是有方向的——**新生产者的数据被老消费者读**（BACKWARD）与**老数据被新消费者读**（FORWARD）是两件不同的事。现存工具要么只给一个布尔 `is_breaking`，要么把方向编码在工具私有的档位名里，跨格式对不上。
3. **"谁会炸"没人归因**：删字段这件事，在"先发消费者、后发生产者"和"先发生产者、后发消费者"两种发布顺序下，砸的是完全不同的人。HN 上 Revolut 的复盘原话就是"删掉一列『没用的』"导致**上一版**认证服务在灰度期间报错。

### 1.6 与已占位工具的四点差异（如实记录，不宣称首创）

1. **跨格式归一**：一个"删字段"在三种 IDL 里得到**同一个规则 ID、同一套方向性判定、同一句修复动作**；现有工具每家只读自家格式。
2. **方向性 + 归因**：判定结果不止 `is_breaking`，而是 `OLD_CONSUMER / NEW_CONSUMER / BOTH / REPLAY_ONLY` 四态归因，并随发布顺序改变（依赖 M4）。
3. **字段号复用检查**：`buf` 不做跨 message 字段号复用；本题把 reserved 与字段号冲突作为一等规则（R5）。
4. **双文件零部署**：`compat a b --policy backward`，不需要 registry、不需要 Kafka、不需要服务端。

**技术栈（✅ 成熟依赖）**：Python 标准库 + `protobuf` 的 `google.protobuf.descriptor_pb2`（`FileDescriptorProto`）解析；Avro 直接吃 JSON（`.avsc`）；JSON Schema 走 `dict` 树。不需要 `.proto` 编译器（`protoc`）：如需 `.proto` 输入，用可选路径调用 `protoc --descriptor_set_out`，**缺失时退出码 3，不降级猜测**。

## 二、任务要求

首期 **5 个模块**，扩展项另列。**所有模块共享同一份数值口径**（七档策略定义、buf 四档映射、七类破例规则、`runtime-dependent` 标注条件、归因四态、退出码矩阵）——口径只在 `data/README.md` §四定义一次，代码与文案不得另立第二套。

### 模块① 三解析器 → 统一 IR

- **输入**：三份 schema 文件中的任意两份（`.avsc` / `.proto` 或 `FileDescriptorSet` / `.json` JSON Schema），各自独立解析。
- **输出**：同构 IR（`ContractIR`）：`fields[*]` 含 `name` / `number`（Protobuf/Avro 字段位置） / `json_pointer`（JSON Schema）/ `type` / `cardinality`（`required` / `optional` / `repeated` / `nullable`）/ `default` / `enum_values[{name, number}]` / `reserved_numbers` / `reserved_names` / `oneof_membership` / `aliases`。
- **引擎**：Protobuf 走 `FileDescriptorProto`（`descriptor_pb2`）；Avro 直接吃 JSON（`fields` / `default` / `aliases` / `symbols`）；JSON Schema 走 `dict` 树（`properties` / `required` / `type` / `enum` / `oneOf` / `$ref` 仅在可解析范围内展开）。
- **确定性纪律**：IR 字段顺序按 `(number 若存在, json_pointer, name)` 规范排序；不读文件系统时间、不写绝对路径；**同一文件两次解析逐字节一致**；无法表达的 JSON Schema 构造（如 `patternProperties`、`if/then`、递归 `$ref`）必须落 `ir_unsupported[*]` 并在报告里显式输出，**不得静默忽略**（getsentry 的 README 自述正是踩了这个坑）。
- **验收**：三种格式各自的 fixture 解析成同构 IR（字段名 / 字段号 / 类型 / 基数 / 默认值 / enum 编号 / reserved 七项齐全）；一个"故意不可表达"的 JSON Schema 用例必须产出 `ir_unsupported` 而非空 IR；同机双跑输出一致。

### 模块② 方向性判定核

- **输入**：`ContractIR(producer_old)` + `ContractIR(producer_new)` + `--policy`。
- **输出**：每个差异项的 `direction` ∈ `{BACKWARD_OK, FORWARD_OK, BOTH_OK, NONE_OK}` 判定，以及该 policy 下的 `verdict` ∈ `{compatible, breaking}`；`--policy` 支持七档：`backward` / `backward-transitive` / `forward` / `forward-transitive` / `full` / `full-transitive` / `none`（语义对齐 Confluent 七档，定义见 `data/README.md` §4.1）。
- **buf 四档映射表**（必须随输出打印，`--explain-mapping`）：

  | 本题 policy | 语义 | 最接近的 buf 档 | 差异说明 |
  |---|---|---|---|
  | `backward` | 新生产者 → 老消费者可读 | `WIRE`（`WIRE_JSON` 对 JSON 视图） | buf 只判 Protobuf 线上字节，不含 Avro/JSON Schema |
  | `forward` | 老数据 → 新消费者可读 | 无直接对应（buf 不区分方向，只判"是否破坏"） | 本题显式区分方向 |
  | `full` | 双向都成立 | `WIRE` + `WIRE_JSON` 同时通过 | buf 的"档"是检查范围，不是方向 |
  | `none` | 只列差异不判定 | — | — |

  映射表**只表达"最接近"，不宣称等价**：buf 的档位是"检查哪些规则"，Confluent 的档位是"允许哪个方向"，两者维度不同——这正是本题要归一的理由。
- **transitive**：与上一版本比较 = 与所有历史版本比较（需要 `--history` 传入版本序列；缺 `--history` 时 `--policy *-transitive` 以退出码 2 拒绝，**不降级为单版本**）。
- **确定性纪律**：判定只依赖两份 IR（+ 可选历史 IR 列表），不依赖输入文件名、文件顺序、主机；差异项排序固定；同一输入两次运行逐字节一致。
- **验收**：同一个"删字段"在三格式下给出**语义一致**的方向性判定（backward 破、forward 不破）；七档策略各自有用例；`--policy=NONE` 输出全部差异但 `verdict` 恒 `compatible`；缺 `--history` 时 transitive 退出码 2。

### 模块③ 破例规则库

- **输入**：`DiffIR`（M2 产出的差异项）。
- **输出**：每条破例一条记录：`rule_id` / `rule_name` / `stable_path`（Protobuf 字段号、Avro 字段名、JSON Pointer）/ `severity` ∈ `{breaking, runtime-dependent, non-breaking}` / `format_evidence`（该规则在三格式下各自的证据形态）。
- **七类规则**（口径唯一定义在 `data/README.md` §4.3）：

  | rule_id | 名称 | Protobuf 表现 | Avro 表现 | JSON Schema 表现 |
  |---|---|---|---|---|
  | R1 | `FIELD_REMOVED` | 字段号消失且未 `reserved` | 字段从 `fields` 消失；**改名未声明 `aliases` 时判定为 remove + add** | `properties` 键消失 / 从 `required` 移除 |
  | R2 | `TYPE_CHANGED` | wire 兼容性（`FIELD_WIRE_COMPATIBLE_TYPE`）与非兼容类型改 | type + logicalType 变化 | `type` 变化 / `format` 变化 |
  | R3 | `REQUIREDNESS_CHANGED` | `optional↔required`、加无默认字段 | 加字段无 `default` | `required` 列表增删 |
  | R4 | `ENUM_NARROWED` | enum 值删除 / 改名（`ENUM_VALUE_SAME_NAME`） | `symbols` 删除 | `enum` 列表收窄 |
  | R5 | `FIELD_NUMBER_REUSED` | 字段号复用（含跨 message 复用）或与 `reserved` 冲突 | 无字段号（`N/A`，显式标注） | 无字段号（`N/A`，显式标注） |
  | R6 | `ONEOF_MOVED` | 字段进出 oneof / oneof 改名 | union 分支移动（`N/A` 时显式标注） | `oneOf` / `anyOf` 分支移动 |
  | R7 | `DEFAULT_CHANGED` | 默认值变更 | `default` 变更 | `default` 变更 |

  > R1 里"Avro alias 缺失"是**同一破例的 Avro 表现**，不单列第八条规则——这正是归一的意义：一个语义、三种证据形态、同一修复动作（`alias`）。
- **`runtime-dependent` 必须显式标注（红线③）**：`severity` 是三值，**不得压成 breaking / non-breaking 二选一**。标注条件（唯一定义在 `data/README.md` §4.4）：判定为"静态必破，但真实数据流可能永不触发"的规则命中（典型：enum 收窄、`required` 加在恒有值字段上、`oneof` 移动但消息体从不带该成员）一律标 `runtime-dependent`，并附 `why_static_breaking` 与 `what_would_trigger` 两段文字。**`--strict-runtime-dependent`（默认开）时 `runtime-dependent` 计入退出码 1**；关闭时它仍必须出现在输出的每一张表里（可关判定强度，不可让条目消失）。
- **确定性纪律**：规则命中只由 IR 与规则表决定；规则表是数据（`rules/` 目录下的定值表），不是散落在代码里的 if；同一输入两次运行规则命中顺序一致（按 `rule_id` 再按 `stable_path` 排序）。
- **验收**：每条规则三格式**各有用例**（含"该格式不适用 → 显式 `N/A`"的用例）；`runtime-dependent` 用例断言三件事：出现在输出、带两段说明、在 `--strict-runtime-dependent` 下把退出码推成 1；字段号复用用例覆盖"跨 message 复用"与"与 reserved 冲突"两种，用于证明 buf 覆盖不到的那一格。

### 模块④ "谁会炸"归因 + 修复建议

- **输入**：M2 的方向性判定 + M3 的规则命中 + `--deploy-order`（`consumers-first` / `producers-first` / `simultaneous` / `replay`）。
- **输出**：每条破例的 `blast_radius` ∈ `{OLD_CONSUMER, NEW_CONSUMER, BOTH, REPLAY_ONLY}` + `repair_action`（`reserve` / `alias` / `add-default` / `add-branch` / `bump-and-version`）+ 一句最小修复动作描述（带可执行落点：Protobuf 写 `reserved <n>;`、Avro 写 `"aliases": [...]`、JSON Schema 写 `"default": ...`）。
- **归因规则**：`consumers-first` 部署下，"删字段"砸 `OLD_CONSUMER`（老消费者仍是线上版本，读到新生产者的数据）；`producers-first` 下砸 `NEW_CONSUMER`（老数据进入新消费者）；历史数据重放场景砸 `REPLAY_ONLY`。归因**必须随 `--deploy-order` 改变**，不得硬编码单一结论。
- **确定性纪律**：归因只由（方向性判定 × 部署顺序 × 该格式的字段可寻址性）决定；**同一破例在不同部署顺序下归因不同，必须由用例锁死**；`REPLAY_ONLY` 只在显式给 `replay` 时出现，不默认推断。
- **验收**：同一破例（删字段 / enum 收窄）在四种发布顺序下各断言一次归因；修复动作必须与该格式的语法落点匹配（三格式各一条 golden 文本）；M3 判 `runtime-dependent` 的条目在归因里同样保留三值语义，不被压平。

### 模块⑤ CLI + 退出码 + JSON/Markdown 报告

- **输入**：`compat <old> <new> --policy <p> --format <md|json> [--deploy-order ...] [--history ...]`。
- **输出**：单张判定表（Markdown 默认 / 规范 JSON 可选）。JSON 为规范形态（固定键序、固定排序、无时间戳/绝对路径/主机名/用户名），Markdown 只是它的渲染视图，**不参与 digest**。
- **退出码矩阵**（唯一定义在 `data/README.md` §4.5，此处为摘录，冲突以 §4.5 为准）：

  | 退出码 | 含义 | 触发示例 |
  |---|---|---|
  | 0 | 该 policy 下无 breaking 项 | `--policy none`；或全部 `non-breaking` |
  | 1 | 有 breaking 项（含默认计入的 `runtime-dependent`） | `backward` 下删字段 |
  | 2 | 用法 / 输入错误 | 未知 policy、`*-transitive` 缺 `--history`、schema 解析失败 |
  | 3 | 环境或能力不满足 | 需 `protoc` 但未安装、JSON Schema 构造不可表达且 `--require-complete-ir` |

  `--ignore-runtime-dependent` 只把 `runtime-dependent` 从"计入退出码"里摘出，**输出条目一律保留**。
- **确定性纪律**：报告不写 `as_of`、不写扫描耗时、不写路径；JSON 键序固定；同一输入两次运行 `diff` 为空；两份报告可 `--verify` 重算 `digest`（`sha256` 于规范化 JSON 字节）。
- **验收**：`data/golden/` 下 golden 逐字节比对（md 与 json 各一份）；退出码矩阵 **0/1/2/3 全覆盖**，每个码至少一条用例，且断言 `3` 的用例必须在"缺 `protoc`"的模拟路径上真跑到；`--verify` 改一字节后非 0 且定位到被改字段。

### 扩展项（不进首期判定路径）

- **混合版本部署矩阵**：N 个版本 × 当前部署版本 → 给出安全发布顺序。依赖 M2 内核，**列二期**。
- **JSON Schema 反例见证**：`L(P) ⊆ L(C)` 的反例输出。**contract-witness（2026-10-17 建仓）与 specwitness 已占**，本题仅作可选输出，不进首期判定路径。

## 六、边界与非目标

- **不做 OpenAPI diff**：oasdiff 1,423★ / openapi-diff 1,098★ / openapi-changes 361★ 已占，且 **optic 1,531★ 已 archived** —— 方向进入市场收敛期，新入者没有增量。
- **不做纯 JSON Schema diff**：红海（`json schema diff` 179 条）+ 反向证据（jsoncompat 两次 Show HN 仅 2 / 7 分、0 评论）。
- **不做纯 Protobuf 破例**：buf 11,491★ 已覆盖全部规则，且规则名已成事实标准；本题只在"buf 空白格"（跨 message 字段号复用、跨格式归一）上增量。
- **不做 Schema Registry 服务**：Confluent 2,470★、Apicurio 944★、karapace 639★ 需部署；本题是**纯本地双文件 CLI**，零 registry。
- **不做 Avro-only**：ExpediaGroup/avro-compatibility 61★ 已占。
- **不做 Thrift**：生态已死（`thrift schema compatibility` 检索 total_count 0），无受众。
- **不做 GraphQL**：graphql-inspector 1,767★ 已占（`schema breaking change` 头部）。
- **不做反例见证器**：contract-witness（2026-10-17 建仓）与 specwitness 已占；且跨格式反例需要编码器，会破坏"纯文件、可复算"的确定性。**仅作扩展项的可选输出**。
- **不做二进制回放验证**：结论取决于采样数据，不可复算——与"同一输入两次运行逐字节一致"的纪律直接冲突。
- **不做运行时拦截 / 代理**：不介入生产流量；本工具只在 CI 与本地读文件。
- **隐私红线**：纯本地、零网络、零注册；报告不写绝对路径、主机名、用户名、时间戳；fixture 全为自建最小 schema，不含真实业务字段。
- **品牌隔离**：文档与代码中不提及本系列其他工具或项目。
- **首期范围限定**：只做 M1–M5；混合版本部署矩阵列二期；JSON Schema 反例见证列可选输出；`.proto` 输入需要 `protoc` 生成 `FileDescriptorSet`，缺失时退出码 3，**不尝试自行解析 `.proto` 文本**（自写解析器是首期最大的伪工作量）。
- **结论纪律**：本工具判定的是"**schema 层面的可读性**"，不是"业务语义正确性"。`runtime-dependent` 的存在正是为此：静态必破不等于线上必炸，报告必须同时给出触发条件，由人决定是否放行。
